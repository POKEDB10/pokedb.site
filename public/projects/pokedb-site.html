Rebuilding pokedb.site: From Monolith to High-Throughput Zero-Trust Platform

Workload: 20c HTTP Keep-Alive Hardware: Local Core i7, Node v24.21.0 Tool: autocannon 7.15 Status: Production Live

1. Context & Motivation

The original pokedb.site ran as a single 1,200-line server script combining URL shortening, pastebin storage, file uploads, and static landing logic. While functional, it exhibited severe scalability and security bottlenecks under load: disk uploads were handled via Multer directly to local storage, short-link redirects synchronous-persisted click counters causing disk contention, and external CDN dependencies (Google Fonts, unpinned scripts) introduced third-party latency and CSP vulnerabilities.

The v2 overhaul set out with strict engineering constraints: modularize the monolith into a clean tool registry with server.js under 60 lines, move large file transfers entirely to presigned multipart uploads on Cloudflare R2 with zero local disk buffering, migrate persistent state to SQLite with WAL mode, and achieve sub-4ms latency and high throughput on core paths while maintaining a zero-trust security posture.

2. System Architecture

3. High-Throughput Click Buffering

Synchronous database writes on every HTTP 302 redirect create I/O bottlenecks that stall event-loop processing. In v2, click analytics are recorded into a memory ring-buffer (ClickBufferManager) and flushed to SQLite inside an atomic transaction every 1,000ms or when the buffer reaches 500 entries. 

// src/utils/clickBuffer.js
flush() {
  if (this.buffer.length === 0) return;
  const toFlush = this.buffer.splice(0, this.buffer.length);
  const aggregated = new Map();
  for (const item of toFlush) {
    aggregated.set(item.code, (aggregated.get(item.code) || 0) + 1);
  }
  this.storage.transaction(() => {
    for (const [code, count] of aggregated.entries()) {
      this.storage.incrementClicks(code, count);
    }
  });
}

5. 20-Minute Soak Telemetry & Memory Stability

During a sustained 20-minute soak test under constant read/write traffic (links created, scrypt password hashes, paste queries, background sweeper cycles), memory consumption exhibited a one-time ~14 MB RSS step corresponding to V8 heap segment allocation (virtual address reservation for SQLite native buffers) and cache warmup. Following the initial step, both heap and RSS slopes stabilized well beneath the 0.5 MB/min project threshold (zero memory leaks is not claimed; statistical linear regression slope reported).

6. Zero-Trust Security Posture

  • Direct-to-R2 File Uploads: Files bypass Node.js memory and disk entirely via presigned S3 PUT URLs. Multer has been completely removed from production dependencies.
  • Client-Side Cryptography: Pastes and Drop files are encrypted in the client browser using WebCrypto AES-256-GCM. Encryption keys reside in the URL fragment (#k=...) and are never sent to the server.
  • Creation-Time Threat Scanning: Links are screened locally in under 1ms against URLhaus parent domains, followed by asynchronous Google Safe Browsing Lookup v4 with 30-minute verdict caching. The redirect path executes zero external network requests.
  • Content Security Policy: Dynamic nonces are generated per request; inline scripts and styles without nonces are strictly rejected. Offline developer utilities operate with connect-src 'none'.
